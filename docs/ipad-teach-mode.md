# iPad: "Learn something new"

Build notes for the iPad half of `docs/teach-mode-plan.md` (Revision 2 wins), 2026-11-28, written with the code. The server half is in `server/README.md` ("Teach problems", `POST /api/teach`). The own-problem plumbing it builds on is in `docs/ipad-own-problem-and-dispute.md`.

## What the student sees

1. A course's list has a second row under "My own problem": **Learn something new** (`ProblemListView.swift`, `LearnRow`). It opens a sheet with one field, "What do you want to learn?" (1 to 200 characters, the way the server counts: `LearnConcept` in `Models.swift`), Start (off while empty) and Cancel.
2. Start pushes the **lesson screen** (`Views/LessonScreen.swift`, route `CourseRoute.lesson`). It says "Putting a lesson together..." at once. When the lesson arrives the panel appears, the short `spoken` line is said on the base voice (ElevenLabs, then OpenAI, then the device voice; never live), and the practice problem starts being made.
3. The **panel** (`Views/LessonPanel.swift`) holds the title, up to 4 steps, the worked example and the conversation. It is type set by `MathParagraph` (`Views/MathParagraph.swift`), the same view the problem card uses; the lesson text is plain `prompt_plain`-style text read by `MathMarkup`, nothing is drawn as ink. Nothing on it times out; there is no timer in `LessonSession`.
4. The bottom bar (each control 44 pt): a mic (tap once to talk, tap again to send, 30 s limit), an "Ask a follow-up" field with a send button, and the practice control. Every question and answer joins the panel and the answer is spoken.
5. The practice control is "Getting a problem ready..." until the server has a checked problem, then **Your turn**. If the server could not check one it says "I couldn't make a practice problem I'm sure of. Try again?" with a **Try again** button (one tap, one request; there is no automatic retry and no unchecked fallback). A failed call says why in plain words and also offers Try again.
6. **Your turn** pushes the normal `ProblemScreen` with `Problem.practice(...)`: id `own:<course slug>`, the statement as `promptPlain` (drawn by the same parser as every prompt) and the sealed reference in `problemRef`. A **Lesson** button in the action pill opens the panel again as a 360 pt side panel; it stays until its 44 pt close button is tapped.
7. If the server says `practice_expired` (the reference is older than 7 days, or the server key changed) on a look, ask or page report, the practice page shows "This practice problem has timed out." and a **New practice problem** button: it asks the lesson for a new problem and goes back to the lesson screen. The app never falls back to an own problem, so the answer guard is never lost.

## The example is never shown unchecked

`explain` returns the example before its check has finished; the check result comes back with the `practice` reply (`example_checked`). `LessonSession.exampleState` therefore starts `pending`, and the panel reads the example only through `LessonSession.visibleExample`, which is `nil` unless the state is `checked`. Pending shows "Checking the example..."; a rejected example (false, or missing from the reply) is `withheld` and the slot is empty; if the practice call itself failed the slot says the example could not be checked. A rejection is final: a later practice call that accepts the same example does not bring it back, and a later rejection takes a shown one away. The follow-up call sends the example in `lesson_text` only once it is checked (the practice call sends the lesson as `explain` returned it, because the server checks that example). Tests: `LessonSessionTests`; the panel drawn in each state: `LessonGalleryTests`.

## The attempted rule (`Core/Attempt.swift`)

The server refuses the final answer by state until the student has really started (`attempted` on ask, consult and follow-up). The iPad decides it from geometry only, with no handwriting recognition, and errs towards "not yet": a wrong "not yet" keeps the guard on a little longer, a wrong "yes" gives the answer away.

A line of the page (from `LineGrouper`) is **work** when it is part of the main working (not a side calculation), holds at least 4 strokes and is at least 2.5 letter heights wide (a dot, a dash, an "x" or a smudge is not work), and is **not crossed out**: some stroke on the page, at least 60 percent as wide as the rest of the line, runs through at least two of the line's strokes (and at least 40 percent of them), by sideways overlap and by its height range containing the stroke's middle. That catches a strike-through, a slash and a scribble, including one big scribble that the grouper attached to a single line; an underline or a fraction bar runs beside the strokes, not through them.

The page is **attempted** when a work line it holds now is the same ink (`InkLine.isSameInk`) as a work line stored at the last look. `AttemptTracker.look` is called as each look starts (it judges against the previous look, then stores this one); an ask or a page report judges the current page against the last look. So a line still being written, a line edited or erased since the last look, a line seen for the first time and a page just cleared are all "not yet". A re-anchor that moves the page makes the line a new one until the next look sees it. Erase page resets the tracker.

Where it goes (`TutorSession.practiceFields`, only for a practice problem):

- `attempted` and `problem_ref` on ask and consult (and `problem_ref` on watch and live-session), and `recent` (the lesson's last 8 turns, nil when empty) on ask.
- Into the live voice: on connect, and whenever the value changes, `LiveContext.practice(attempted:)` is pushed as a context line ("has not tried yet, do not state the final answer..." or "has now written real work"). The server's live instructions carry the same rule for a teach problem (`LIVE_TEACH_NOTE`); the pushed line keeps the voice right as the student writes and covers the turns where the voice answers without asking the page reader.
- The lesson (`LessonSession.notePracticeAttempted`), so a follow-up asked from the panel carries it too.
- The log: `attempt_changed {attempted, source: look|request|page_erased, work_lines}`; `ask_started` and `live_consult_started` carry `attempted`.

Known limit: a student who copies the problem statement onto the page has written a line, and the geometry cannot tell a copied statement from work. That counts as an attempt after one look. Tests (`AttemptRuleTests`, `PracticeSessionTests`): blank, one stroke, three strokes, a smudge, a side calculation, a finished line, a strike-through, a slash, a tall scribble, one scribble across three lines, an underline, a fraction bar, an edit after a look, erased work, Erase page, and the live context on connect, on attempt and on erase.

## Wire (`Core/TeachWire.swift`, `Core/WireTypes.swift`)

- `TutorClient` has `teachExplain`, `teachFollowup`, `teachPractice` with defaults in a protocol extension that throw `notConfigured`, so the existing test fakes compile unchanged. `HTTPTutorClient` posts all three to `api/teach` with a 45 s timeout; `MeteredTutorClient` passes the allowance through; `ScriptedTutorClient` returns a fixed lesson ("Undoing an operation"), a refusal for "baking bread", a fixed follow-up answer and a fixed practice problem with a fixed reference.
- `explain` request `{action, session_id, course, concept}`; reply, flat: `{is_math, fits_course, message, title, steps, example: {prompt_plain, steps, final_answer}, spoken, model, latency_ms, request_id?}`; when refused, `title`, `steps`, `example` and `spoken` are present and null (`TeachExplainResponse` builds a `lesson` from the flat fields only when title, steps and example are all there). A refusal shows the server's `message`. `followup` request `{action, session_id, course, concept, lesson_text (at most 3,000), recent, question | audio_base64, problem_text?, problem_ref?, attempted?}`; once a practice problem exists the follow-up carries its reference, its statement and `attempted`. `practice` request `{action, session_id, course, concept, lesson_text (the lesson as text, at most 3,000, without the example), example? {prompt_plain, steps, final_answer}}` (the example is its own field, checked by the server); reply `{example_checked, problem: {id, prompt_plain} | null, problem_ref | null, reason}`.
- `problem_ref` is left out of the JSON when nil, on watch, ask, consult, live-session and follow-up; `recent` and `attempted` only on a practice problem's ask (and `attempted` on its consult). The reference is never encoded with a `Problem` and never logged.
- Errors: 422 `practice_expired`, 502 `teach_too_long` ("That came out too long, try again."), 502 `teach_unusable`, 503 `teach_unavailable` have their own `TutorError` cases, found in either the `error` or the `reason` field (`HTTPTutorClient.error`).

## Logs (labels, ids, counts; never student text)

`lesson_requested {course, concept_chars, reason}`, `lesson_shown {latency_ms, steps, example_lines, model, request_id, server_latency_ms}` (the latency is Start tap to panel, measured on the iPad), `lesson_refused {reason: not_math | concept_outside_course}`, `lesson_failed`, `practice_ready {reference: checked, example_checked, trigger, latency_ms, prompt_chars}`, `practice_not_checked {reason, example_checked, trigger}`, `practice_failed`, `example_withheld {reason}`, `lesson_followup {input: typed|voice, chars, recent_turns, latency_ms, answer_chars, attempted}`, `practice_started`, `practice_expired`, `lesson_panel_reopened`, `lesson_panel_closed`, `lesson_closed`, `attempt_changed`, `problem_opened {kind: teach}`. The concept, the follow-up question and its answer appear only in Debug builds (`TutorSession.logsWords`). Release builds keep counts: that is checked in CI by `ios/Scripts/check_release_log.py` (below), not by a Debug run.

## Tests

Unit (XCTest, one class at a time with `-only-testing` on one simulator; the unit tests make no sound because `LaunchOptions.mutesSound` is true under XCTest, asserted first by `LaunchOptionsTests`):

- `LaunchOptionsTests`: every sound is muted under XCTest with no launch argument.
- `AttemptRuleTests` (geometry), `PracticeSessionTests` (a real canvas and a fake tutor: requests, attempted, live context, expiry), `LessonSessionTests` (a fake teach client: the panel, the example states, practice states, recent, follow-ups), `TeachWireTests` (snake_case, `problem_ref` left out, replies decode, error labels, scripted client, `MathParagraph` loses no character), `LessonGalleryTests` (draws the panel states to PNG when `LESSON_GALLERY_DIR` is set).
- A fake that has none of the teach calls (`FakeTutorClient`) still compiles and its teach calls throw `notConfigured`.

UI (CI only, never on the laptop): `PencilTutorUITests/LessonUITests.swift`, launched with `--silent` against the scripted tutor: the row sits under My own problem and above the bank problems and is 44 pt; the sheet needs a concept and Cancel opens nothing; Start shows the panel (title, 4 steps, then the checked example); Your turn opens the page with the practice problem on the card; Lesson opens the side panel, which stays until its close button is tapped; Back returns to the lesson; a follow-up joins the panel; "baking bread" is refused. A rejected example through the real UI is not covered by the scripted client (it always accepts); the unit tests cover the states and the gallery draws the withheld panel.

CI Release check (`.github/workflows/ios.yml`, last step, on by default, turn it off with the `release_log_check` input): builds the Release configuration for the simulator (the app is uninstalled first so Debug logs are gone), runs `LessonUITests/testAFollowUpIsAddedToThePanel` on it, copies the session log out of the simulator and runs `ios/Scripts/check_release_log.py`: none of the canary strings (the typed concept, the follow-up, the scripted lesson, practice problem and reference, the scripted answer) may appear, none of the Debug-only fields (`concept`, `question`, `answer`, `student_said`, `tutor_said`, `text`, `message`, ...) may be present, and the lesson events must exist with their count fields. The script was run here against four hand-made logs (good, with words, with events missing, empty): exit 0, 1, 1, 2. The whole Release build compiled locally (`build-for-testing`, 31 s); the Release UI run itself is unverified until CI runs it. In Release `--silent` is ignored, so that CI run speaks on the runner's (silent) simulator; that never happens on a laptop.
